# GitLab Auto MR 使用说明

本扩展帮助你在 VS Code 中查看远程分支、检查上线版本、搜索分支，按分支合并规则创建 GitLab Merge Request（以下简称 MR），并按项目汇总待自己审批的 MR。

> 扩展支持创建 MR、查看代码 Diff、手动批准及二次确认后的立即合并。不会自动批准或排队等待合并；审批资格、流水线检查和最终合并权限仍由 GitLab 控制。

## 一、使用前准备

### 从源码打包安装

在仓库根目录安装项目依赖后执行：

```bash
pnpm run package:vsix
```

该命令依次运行 `test:publish` 本地逻辑测试、类型检查，再通过固定版本的 VSCE 生成本地 VSIX。发布测试仅包含模板、分支视图、筛选和上线总览，不运行接口请求测试（包括 mock 接口测试）或 HTTP/Git 集成测试。任何必跑步骤失败都会停止；打包时自动执行现有 `vscode:prepublish` 压缩构建。首次使用需要联网下载 VSCE，需 Node.js 22 或更新版本。

本地打包允许缺少仓库地址，并跳过文档相对链接改写，避免因无法识别仓库而中断打包。文档相对链接保留原样，在扩展详情页中不保证可访问；这不会忽略其他构建或打包错误。

安装包按当前 `package.json` 的名称和版本自动命名，例如 `gitlab-auto-mr-0.1.1.vsix`，生成在仓库根目录；更新版本号后无需修改脚本。只包含扩展运行文件、图标和使用文档，不包含源码、测试文件、source map 或本地配置；运行依赖已打入 bundle，因此不额外收集 `node_modules`。

在 VS Code 扩展面板点击 `…` → **从 VSIX 安装…**，选择安装包并重新加载窗口。此命令不会上传 Marketplace，也不会提交代码或创建 Git 标签。扩展目录中的 `pnpm run package` 仍仅执行压缩构建，不生成 VSIX。

### 运行环境

- VS Code 1.80.0 或更新版本，且已安装本扩展。
- 本机可执行 Git；main 合入状态检查需要 Git 2.38 或更新版本。
- 使用 VS Code 打开本地 GitLab 项目，项目已配置 `origin` 远程地址。
- 可访问 GitLab，并具有项目访问及创建 MR 的权限。
- 准备具有 `api` 权限的 GitLab Personal Access Token。
- 本地 Git 能正常拉取 `origin`。Git 拉取凭据与 GitLab API Token 分别配置，仅设置 Token 不代表 Git 拉取已授权。

当前扩展使用工作区中的第一个文件夹作为项目目录。建议直接打开需要操作的项目，避免在多文件夹工作区中选错仓库。

## 二、首次配置

### 1. 配置 GitLab 地址

1. 打开 VS Code 设置，搜索 `gitlabMr.instanceUrl`。
2. 填写 GitLab 实例地址，例如 `https://gitlab.example.com`。
3. 不要添加 `/api/v4` 或项目路径。

也可在命令面板中搜索 **GitLab MR: Configure GitLab Server Address** 打开该设置。

使用 GitLab.com 时保留默认地址。如果配置仍为默认的 `https://gitlab.com`，扩展会尝试根据远程仓库地址识别私有 GitLab 主机。

### 2. 配置 Access Token

1. 按 `Ctrl + Shift + P` 打开命令面板。
2. 搜索 **GitLab MR: Set Access Token**。
3. 输入具有 `api` 权限的 Token，回车保存。

**凭据注意事项：**

- Token 只写入 VS Code SecretStorage，不会写入用户设置、工作区设置或仓库文件。底层由系统凭据库或当前 VS Code 运行环境的安全存储管理。
- 升级旧版本时，插件会先把旧 `gitlabMr.accessToken` 迁移到 SecretStorage，成功后清除用户、工作区和工作区文件夹范围内的明文配置。
- Token 按 GitLab 实例隔离。更换 Token 时重新执行 **Set Access Token**；清除时执行 **Clear Access Token**。
- Remote SSH、容器或 Codespaces 窗口使用各自运行环境的 SecretStorage，首次进入新的运行环境可能需要重新录入。

### 3. 打开 GitLab 工作台

点击 VS Code 活动栏的 **GitLab 工作台** 图标，其中包含 **分支管理**、**上线总览**、**我的待办** 和 **操作审计** 四个视图。原“上线检查”分支视图现更名为“分支管理”，原有命令 ID、过滤条件和工作区状态保留。

首次安装会自动打开功能引导。需要重新查看时，在命令面板运行 **GitLab MR: Getting Started (打开功能引导)**，可逐步进入 GitLab 配置、Token、分支管理、我的待办、上线总览、冲突处理和操作审计。

已配置 Token 时会自动加载项目的完整远程分支列表，第一层不需要点击“加载更多”；只有分支下的第二层检查结果分页。首次未配置 Token 或未加载分支时，可以使用视图中的加载入口或命令 **GitLab MR: Check Release Readiness**。

## 三、界面与常用入口

加载分支后的内容区域示意：

```text
分支管理
  搜索分支
  feature
    2.8.0
      PROJ-123
        login
  main
  release
    2.8.0
```

分支按 `/` 分层展示，目录默认折叠。例如 `feature/2.8.0/PROJ-123/login` 会拆分为四层，最后一层才是真正的分支节点。

真实分支名称后显示最新提交的作者（GitLab commit 的 `author_name`，并非分支创建者）和提交时间（`committed_date`，按本机时区展示）。远程分支列表及 release 下已加载的 feature 分支均支持，原有当前选择、MR 状态及 main 合入标记保留。悬停可查看完整信息及带时区的原始时间。信息随分支列表加载、刷新、搜索和 feature 分页更新，不额外逐分支请求；目录不显示。接口缺失或返回无效字段时显示“作者未知”或“时间未知”并记录日志；只有历史 MR、未返回对应分支数据的结果不显示提交信息。

行内展示为 `张三 · 提交时间 · 5分钟前更新`，不添加“最新作者”前缀，也不展示或查询创建者。姓名保留原始作者名，不截断；悬停可确认这是最新提交作者，**不代表最后推送者**。

更新时间间隔以最新提交的 `committed_date` 与当前时间比较：不足一分钟显示“刚刚更新”，不足一小时显示整分钟，不足一天显示整小时，超过一天显示整天（向下取整）。每分钟自动刷新显示，不请求 GitLab；保留完整提交时间以便核对。无效时间不计算间隔，未来提交时间显示“提交时间晚于当前时间”，避免误报。该间隔反映最新提交时间，不代表最后推送或创建分支的时间。

| 入口 | 用途 |
| --- | --- |
| 内容第一行“搜索分支” | 输入关键词发起远程搜索，自动加载全部匹配分支 |
| release 子结果中的“加载更多” | 加载该版本 feature 和该 release MR 的下一页，各最多 100 条 |
| 标题栏漏斗图标 | 选择常用分支过滤条件 |
| 标题栏检查图标 | 从全部已加载远程分支中搜索选择并检查 |
| 标题栏刷新图标 | 重新获取远程分支，并更新当前所选分支的检查结果 |
| 分支行内或右键的检查入口 | 检查该分支，结果显示为它的子节点 |
| 分支行内复制图标或右键“复制分支名称” | 将完整分支名复制到剪贴板，支持远程分支及 release 下的 feature 结果 |
| 符合条件的分支行内或右键的“创建 MR” | 固定该分支为源分支，按合并规则推荐目标 |
| 启用删除开关后，已合入 main 分支的垃圾桶或右键删除入口 | 确认并重新检查后删除远程分支，保留本地分支 |
| 左下角状态栏“GitLab MR” | 进入通用创建 MR 流程，自行选择源分支与目标分支 |

部分行内按钮需要鼠标悬停在分支上才显示，也可以通过右键菜单操作。

复制的是完整名称（例如 `feature/2.8.0/PROJ-123/login`），不是当前层级的短名称。release 下的 feature 结果复制该 feature 名称，而非所属 release。目录不提供复制入口；复制不需要 Token，也不受删除开关或合并状态限制。点击分支名称仍执行原有检查或 MR 操作。

### 待我审批

在活动栏 **GitLab 工作台** 对应的侧边栏中，展开 **待我审批** 视图：

```text
待我审批
  group-a/project-a    2 个待审批
    !12 修复登录问题    feature/login → release/v1 · 提交人: 张三 (@zhangsan)
    !16 调整表单逻辑    feature/form → release/v1 · 提交人: 李四 (@lisi)
  group-b/project-b    1 个待审批
    !8 优化流程配置     feature/workflow → main · 提交人: 王五 (@wangwu)
```

- 范围：当前 GitLab 实例中，当前 Token 用户被指定为 **Reviewer** 的全部可见项目，不限于本地工作区的项目。
- 条件：MR 状态为开放（`opened`），并且审批记录 `approved_by` 中没有当前用户。即使其他人已批准或已满足整体审批数量，只要自己尚未批准仍会显示；本人已批准的 MR 不显示。草稿 MR 保留，并标注“草稿”。
- 分组：第一层是完整项目路径（含命名空间），第二层为 MR 项目内编号 `!IID` 与标题，行内展示 `Source → Target` 和提交人姓名/用户名；悬停可查看完整分支、提交人及 GitLab 全局 `ID`。点击或展开 MR 后加载变更文件，点击文件在 VS Code 中查看只读双栏 Diff；行内外链图标仍可在浏览器打开 MR。
- 首次显示且已有 Token 时自动加载。标题栏刷新按钮或命令 **GitLab MR: Refresh Pending Reviews** 重新查询；在 GitLab 完成审批或撤销审批后请刷新。查询中重复点击不会重复请求。
- 沿用 `gitlabMr.instanceUrl` 和现有 Token。配置保留默认 GitLab.com 时，有 Git 工作区会根据 `origin` 探测实例；没有工作区也能使用显式配置的 GitLab 实例。无需拉取代码或本地存在各项目仓库。
- 所有候选 MR 自动分页获取，每页 100 条；逐个查询审批记录，并发上限 5。同一轮查询每个待展示项目只获取一次详情。
- 未配置 Token 时显示配置/加载入口，主动刷新可录入 Token。修改实例或 Token 会清除旧结果，可见时重新加载，旧查询的迟到响应不会覆盖新结果。
- 无待审批项时明确提示。整体查询失败显示错误及重试入口；部分审批状态或项目查询失败时保留已确认结果，显示“结果不完整”和失败 MR，不把未确认项计入待审批数量。若实例版本、许可或权限不支持审批接口，会提示而不是把失败当作“尚未批准”。

该视图仅汇总被指定为 Reviewer 的 MR，不包含仅作为 Assignee、审批规则候选人但未被指定为 Reviewer 的 MR；也不替代 GitLab 的实际审批资格、保护规则、流水线或最终合并权限检查。

#### 在 VS Code 中查看代码

1. 点击或展开 MR，加载该 MR 当前 Diff 版本的文件列表，标记新增、删除、修改和重命名。
2. 点击文件，左侧展示 MR 合并基线的完整文件，右侧展示源分支审阅提交的完整文件；新增文件左侧为空，删除文件右侧为空，重命名使用各自路径。支持跨项目及 fork MR，无需本地克隆或切换分支。
3. 文件通过 GitLab API 按固定提交 SHA 读取，虚拟文档为只读，不写入本地项目。查看期间远程推送不会悄悄替换已加载的审阅版本；需要最新代码时刷新列表并重新打开变更。
4. 二进制、非 UTF-8、文件读取失败明确报错，不以空文件代替。若 GitLab 版本接口返回的文件列表被截断或无法确认完整性，会显示警告并阻止在扩展内批准或合并，请使用浏览器审阅。
5. Diff 版本未就绪、仓库被删除、权限不足或接口不支持时显示错误，可点击失败行重试或使用浏览器入口。刷新列表及切换实例/凭据会使旧 MR、文件操作失效，需重新选择；已打开的编辑器可能仍保留旧版本文本，请勿将它当作最新代码。

#### Approve（批准）

1. 先加载并查看 MR 的变更，确认已审阅所展示版本的所有文件。
2. 点击 MR 行内的 **Approve MR（批准当前审阅版本）** 对勾或右键同名菜单。
3. 模态确认框展示项目 ID、MR 和审阅提交 SHA；确认后重新校验 MR 仍开放、自己仍为 Reviewer，以及源/目标 Diff 引用未改变，再带该 SHA 请求 GitLab 批准。
4. 代码已变化时不批准，需刷新并重新审阅；GitLab 在提交请求时还会用 SHA 校验源分支版本，冲突返回错误。此操作**不合并 MR**，也不自动绕过审批权限或规则。
5. GitLab 明确确认本人批准后提示成功并刷新列表；成功但刷新失败时，保留批准成功提示及列表错误，不重复批准。网络错误或响应未确认时结果可能未知，请刷新或到 GitLab 核对，不要盲目重试。

需要重新认证、审批密码、SAML 或权限受限的项目，请通过浏览器入口完成批准。不会保存审批密码，也不自动重试写入请求。Diff 加载并不代表已自动完成代码评审，是否批准由用户在确认框中决定。

#### Merge（立即合并）

1. 先展开 MR 并查看当前版本的完整变更，再点击行内合并图标或右键 **Merge MR（立即合并已审阅版本）**。
2. 模态确认框显示 MR 编号、项目、源 → 目标分支和审阅 SHA。确认即请求写入目标分支，沿用 MR 在 GitLab 上已有的 squash 和删除源分支设置，不套用本扩展的创建 MR 默认配置。
3. 提交前重新请求 GitLab 检查合并状态，并校验 MR 仍开放、自己仍为 Reviewer、源/目标项目与分支及所有 Diff 引用未变化。GitLab 必须明确返回 `detailed_merge_status: mergeable`、`has_conflicts: false`、`user.can_merge: true`，且非草稿/WIP；缺失或未知状态同样阻止，不猜测权限或可合并性。
4. 合并请求携带已审阅 SHA，明确关闭自动合并及等待流水线；不自动执行 Approve，不绕过审批、保护分支、冲突、流水线或讨论解决规则。状态重新计算可能是异步的，若返回 checking 等状态请稍后刷新重试，最终仍由 GitLab 接口执行权限和规则检查。
5. 仅当响应确认对应 MR 已 `merged` 且 SHA 一致时提示成功并刷新列表。重复点击或并发批准/合并被阻止；响应未确认或网络错误时提示结果未知，不自动重试。审计准备记录无法落盘时不会发送合并请求；成功后审计失败会明确提示，不要重复合并。

本视图仍只展示**本人尚未批准**的 MR。本人执行 Approve 后该 MR 会离开列表；需要本人批准才能满足规则的 MR，请批准后到 GitLab 页面合并，不会在此自动串联“批准并合并”。如果其他人已满足审批规则而自己尚未批准，且自己有合并权限，则可在此按上述条件直接合并。旧 GitLab 版本未提供所需状态/权限字段时，请使用浏览器入口。

## 四、查找与过滤分支

### 1. 常用分支过滤

点击标题栏的漏斗图标，多选需要显示的分支类型。

默认条件：

```text
feature/、release/、dev、uat、main、bugfix/、hotfix/、tst、pre
```

匹配规则：

- 以 `/` 结尾：匹配对应目录下所有层级，例如 `feature/`。
- 其他条件：精确匹配，例如 `dev` 不匹配 `develop` 或 `dev/test`。
- 取消全部勾选并确认：取消常用分支过滤，显示当前搜索范围内的全部分支。
- 按 Esc：取消本次修改。

常用分支过滤保存在当前工作区，刷新及重启后保留。

### 2. 关键词二次过滤

1. 点击内容区域第一行 **搜索分支**。
2. 输入关键词，例如 `2.8.0`、`PROJ-123` 或 `hotfix`。
3. 回车确认。

关键词提交给 GitLab 进行远程搜索，匹配语义以 GitLab 的分支搜索为准；支持用 `^`、`$` 约束开头和结尾。匹配分支的父目录仍会保留，便于定位。这样可以查找尚未加载到本地列表的远程分支。

两层条件叠加生效。例如仅勾选 `release/` 时，搜索 `PROJ-123` 不会显示被第一层排除的 feature 分支。

- 修改关键词：再次点击“搜索分支”。
- 清除关键词：清空输入框并回车。
- 按 Esc：保持原关键词。
- 无匹配分支：仍保留搜索入口，可修改或清空关键词。
- 刷新：保留关键词。
- 重启扩展：清空关键词。

修改或清空关键词会重新请求远程并自动读取全部匹配分支，清空旧列表、检查结果及 main 标记。常用分支过滤只处理远程已经返回的数据，不产生请求。视图不额外展示顶部过滤条件提示。

### 3. 加载更多与重试

- 第一层分支列表自动加载完整数据，不提供分页按钮。若中途失败，保留已返回数据，点击“重试加载分支”自动继续读取剩余数据。
- 第二层 release 检查结果底部点击“加载更多”，每次从尚未结束的 feature 和 MR 来源各追加最多 100 条。
- 第二层加载失败时保留成功加载的页面，点击失败提示重试同一页。
- 正在加载时入口不可重复点击；切换搜索后，旧搜索请求的迟到结果不会覆盖新结果。
- 刷新保留当前关键词，重新加载完整第一层列表；第二层检查分页从第一页重新开始。
- 第二层最后一页不足 100 条时停止显示加载更多；恰好 100 条可能需要再点击一次，返回空页后确认加载完毕。

## 五、检查分支状态

### 1. 检查普通分支

展开目录找到目标分支，点击其行内 **检查上线分支合并状态** 按钮，或使用右键菜单。点击分支名称也会触发检查。

检查结果直接显示在该分支下一级，并自动展开：

```text
dev
  最新代码已全部合入 main
```

也可能显示：

- `尚有代码未合入 main（或存在合并冲突）`
- `main 合入检查失败: ...`
- 对 main 自身显示 `当前分支为 main，无需检查合入自身`

最新内容已全部合入远程 main 的分支，会显示绿色通过图标及 **代码已合入 main** 标记。目录和 main 自身不显示这个绿色合入标记。

此判断基于模拟合并后的代码树，不是单纯比较提交 SHA 或历史 MR 状态，支持 squash/rebase。未标绿不一定代表从未合并，也可能有新增改动、冲突或检查失败。

### 2. 检查 release 分支

检查 `release/2.8.0` 或 `release/2.8.0/hotfix` 时，除 main 合入状态外，还会检查同版本 feature 分支的 MR 状态。

版本号取路径第二段。例如以上两个 release 都匹配 `feature/2.8.0/...`，但查询的 MR 目标分别为所点击的完整 release 分支。

示意结果：

```text
release
  2.8.0
    尚有代码未合入 main（或存在合并冲突）
    feature/2.8.0/PROJ-101    已合并
    feature/2.8.0/PROJ-102    MR 开放中
    feature/2.8.0/PROJ-103    MR 已关闭未合并
    feature/2.8.0/PROJ-104    尚未创建 MR
```

| 状态 | 含义与操作 |
| --- | --- |
| 已合并 | 已有合并到该 release 的 MR，可打开查看 |
| MR 开放中 | 存在以该 release 为目标的开放 MR，可打开处理 |
| MR 已关闭未合并 | MR 已关闭但未合并，可打开查看或重新创建 |
| 尚未创建 MR | 未找到对应 MR，可创建目标为所属 release 的 MR |

**分页完整性：** release 检查分别读取同版本 feature 和对应 MR 的第一页，每个来源最多 100 条；结果末尾的“加载更多”继续读取尚未结束的数据源。该查询独立于列表的关键词搜索。MR 尚未全部读取时，feature 显示“MR 状态待确认”，不提供固定目标为 release 的补建操作，避免漏读后续 MR 而重复创建。MR 全部加载后才确认已加载 feature 的状态；feature 分页也结束后才算完整版本检查。期间会显示“结果尚未完整”，不要用局部统计作为完整版本结论。

所有 feature 均已合并时仍显示结果；没有匹配 feature 时，在该 release 下显示提示。检查失败时显示失败原因，而不是把旧结果当作本次成功结果。

**注意区分两个维度：** feature 行上的 MR 状态描述“是否合入所属 release”；绿色 main 标记描述“代码是否已进入 main”。两者独立，不可互相替代。

### 3. 结果保留与刷新

- 检查不同分支时，结果分别挂在各自分支下，不再生成顶部独立的检查节点。
- 切换选择不会清除其他分支结果。
- 日常单分支检查使用已加载列表，只同步当前分支和 main；release 额外查询自身的 MR。
- 首次加载、刷新及远程搜索完整返回分支列表后，自动检查返回分支的 main 合入状态，显示已合入的绿色标记；main 无须出现在搜索结果中。此过程只同步返回分支与 main 的引用，不修改工作区。
- 日常点击检查或推荐创建入口时仅更新当前分支；第二层“加载更多”不会重新扫描 main，也不会清除其他分支的绿色标记。自动标记检查失败时提示并保留列表，但不显示失效标记。
- 刷新会清除旧子结果、重新获取完整分支列表，仅在当前所选分支仍位于列表中时检查它。
- release 的“加载更多”只获取下一页数据，不重复执行 main 检查；失败时保留已加载页并允许重试。
- 远程新增或删除分支后，应点击刷新。
- 检查不会切换本地分支，也不会修改工作区文件或暂存区。

### 4. 删除已合入 main 的远程分支

1. 在 VS Code 设置中启用 `gitlabMr.allowBranchDeletion`（默认 `false`）。关闭时不显示删除入口，即使直接调用命令也不能删除。
2. 在已标记 **代码已合入 main** 的远程分支或 release 下的 feature 结果上，点击垃圾桶图标或右键选择 **删除已合入 main 的远程分支**。
3. 在模态确认框中点击 **删除远程分支**。取消不会执行删除。
4. 扩展重新拉取该分支与 main，使用模拟合并代码树检查最新内容。未合入、冲突、缺少 main、拉取或 API 失败均会中止并提示。
5. 扩展核对 GitLab 分支提交与本次检查使用的提交一致，禁止删除 main、项目默认分支和受保护分支。GitLab 还会校验 Token 的删除权限。
6. 删除成功后，分支列表和已加载的 release 子结果移除该分支；不会删除本地分支，也不会切换分支、修改工作区或暂存区。

判断依据是最新代码已进入 main，**不是**“曾经有一个已合并 MR”，也不是“仅合入了 release”。支持 squash/rebase。检查期间检测到分支或 main 已更新时会取消删除，需刷新后重试。GitLab 删除接口不支持按提交 SHA 原子条件删除，因此最终 API 校验与删除之间仍存在并发更新窗口，清理期间应避免其他人继续推送。

此开关仅控制手动删除；现有 `gitlabMr.removeSourceBranch` 仍独立控制创建 MR 时是否勾选“合并后删除源分支”，默认值不变。

## 六、创建 Merge Request

### 方式一：从分支创建，推荐目标

适用于视图中未标记为已合入 main 的分支。

1. 在分支行内或右键菜单中选择 **创建 MR（按合并规则推荐目标分支）**。
2. 扩展重新检查该分支是否已合入 main；已合入时更新标记并提示，不继续创建。
3. 以点击的分支为源分支，展示推荐目标列表。
4. 选择目标分支。
5. 确认或修改自动生成的标题，回车创建 MR。
6. 在 GitLab 中审核、检查流水线并最终合并。

该入口**不固定目标为 main**。目录、main 自身、已标记为合入 main 的分支不显示该入口。main 不必出现在当前搜索结果中；若实际远程缺少 main，重新检查会报错，不继续创建。此时如需创建其他方向的 MR，可使用状态栏的通用入口。

### 方式二：从 release 检查结果补建 MR

在 release 下的 feature 检查结果中，完成 MR 分页后，为确认处于“尚未创建 MR”或“MR 已关闭未合并”的项执行 **为该功能分支创建 MR**。

此操作固定：

- 源分支：所点的 feature。
- 目标分支：该结果所属的完整 release 分支。

不需要再次选择目标，确认标题后创建。创建流程结束后会重新检查所属 release。

### 方式三：通用创建入口

1. 点击左下角状态栏 **GitLab MR**，或运行 **GitLab MR: Create Merge Request**。
2. 选择源分支，默认聚焦当前本地分支。
3. 选择目标分支，推荐项在前。
4. 确认标题后创建。

该流程使用本地及已获取的远程分支引用。创建前应确认源分支代码已推送，目标分支在 GitLab 中存在；扩展不会代替你推送代码。

### 目标推荐规则

| 源分支类型 | 优先推荐目标 |
| --- | --- |
| feature / bugfix | release；路径第二段相同的 release 优先 |
| release / hotfix | 测试环境分支和 main/master |
| conflict | 测试环境分支和 release |
| revert | 测试环境分支、release 和 main/master |
| main / master | 测试环境分支和 release，用于基线回流 |
| 其他 | 默认目标优先，其余可选 |

常见测试环境包括 dev、tst、uat、pre 等。同一推荐级别下，配置的默认目标优先。不会自动创建或合并 MR。

`gitlabMr.hideNonConformingTargetBranches` 默认 `true`：目标选择列表仅显示符合上表合并方向的分支，不合规的默认目标也会隐藏。feature/bugfix 仍可选择其他版本的 release，同版本仅优先排序，并非唯一允许的版本。此配置沿用现有分支类型识别规则，不增加新的分支命名校验。

未知源分支类型或没有符合规则的候选时，会提示并停止，不会自动退回全部候选。可将此配置设为 `false`，恢复“推荐优先、其余分支仍可选择”的行为，未知类型则默认目标优先。此过滤对通用创建及从分支推荐创建的目标选择均生效，不影响源分支选择、远程分支浏览或 release 检查中固定目标的补建 MR。

### 标题、描述与创建结果

扩展按分支组合生成标题，例如：

| 合并方向 | 标题示例 |
| --- | --- |
| feature → release | `(feature-release) PROJ-123 优化登录流程` |
| release → uat | `(release-uat) release/2.8.0 合并到 uat` |
| release → main | `(MTP-CRQ123456) release/2.8.0/CRQ123456 Move To Production` |

若标题中出现 `<Jira号>`、`<JIRA号>` 或 `<CRQ>`，请在确认前补充实际编号。未知合并组合使用配置的兜底标题模板。

描述会聚合提交历史、变动文件及自测清单。提交历史超过 10 条时，使用默认收起的 `<details>` 折叠整个列表，点击“点击展开提交历史”可查看全部提交；10 条及以内直接展示，不截断记录。所有创建入口均按 `gitlabMr.defaultReviewers` 中配置的 GitLab 用户名指定 Reviewer。例如在设置中填写 `["zhangsan", "lisi"]`，提交时会自动解析账号并通过 Reviewer 字段指派，不作为 Assignee。用户名支持前后空格及可选 `@`，相同账号只指派一次。空列表表示不指定 Reviewer；非空配置必须全部匹配成功，否则中止创建并提示错误，避免遗漏审核人。

创建成功后会通知 MR 编号，并提供打开浏览器、复制链接和查看日志等操作。默认会自动打开浏览器。

取消目标选择或标题确认不会创建 MR。

## 七、外部工单链接

release 检查结果中的 feature 分支支持工单链接：

- 从 `feature/<版本>/<工单号>/...` 的第三段提取编号。
- 匹配 `gitlabMr.issueLinks` 中配置的正则表达式。
- 有匹配链接时，展开 feature 结果节点，点击工单链接跳转。

自定义配置示例：

```json
{
  "gitlabMr.issueLinks": [
    {
      "name": "Jira",
      "pattern": "^([A-Z][A-Z0-9]*-\\d+)$",
      "urlTemplate": "https://jira.example.com/browse/{id}"
    }
  ]
}
```

请将示例地址替换为实际工单系统地址。`{id}` 会替换为匹配到的工单编号。

## 八、常用设置

在 VS Code 设置中搜索 `gitlabMr`。

| 设置 | 默认值 | 说明 |
| --- | --- | --- |
| `gitlabMr.instanceUrl` | `https://gitlab.com` | GitLab 实例地址 |
| `gitlabMr.defaultTargetBranch` | `master` | 默认目标；参与推荐排序，不强制使用 |
| `gitlabMr.hideNonConformingTargetBranches` | `true` | 目标选择时隐藏不符合内置合并规则的分支；关闭后恢复全部候选 |
| `gitlabMr.defaultReviewers` | `[]` | Reviewer 用户名列表，不需要 `@` |
| `gitlabMr.titleTemplate` | `Merge ${sourceBranch} into ${targetBranch}: ${latestCommitTitle}` | 未命中内置规则时使用 |
| `gitlabMr.removeSourceBranch` | `true` | 创建 MR 时设置合并后删除源分支 |
| `gitlabMr.squash` | `false` | 创建 MR 时是否启用 squash |
| `gitlabMr.autoOpenInBrowser` | `true` | 创建成功后自动打开浏览器 |
| `gitlabMr.issueLinks` | 内置 Jira、ITSM 规则 | 工单编号匹配与跳转地址 |

> 默认启用“合并后删除源分支”。对于需要长期保留的源分支，请在创建前调整配置，并在 GitLab MR 页面再次确认。

## 九、常见问题

### 看不到需要的分支

依次检查：

1. 代码是否已推送到当前项目的 origin。
2. 是否需要点击刷新更新完整远程分支列表；只有 release 检查子结果需要“加载更多”。
3. 常用分支过滤是否排除了该分支。
4. “搜索分支”中是否保留了关键词，可清空后重试。
5. 是否打开了正确工作区，尤其是多文件夹工作区的第一个文件夹。

### API 可用，但 main 检查失败

main 检查通过本地 Git 执行拉取和模拟合并。确认：

- 远程存在 main；仅存在 master 不会被自动当成 main。
- 本地 Git 版本至少为 2.38。
- Git 拉取 origin 的网络和凭据正常。
- GitLab API Token 并不能代替 SSH 密钥或 Git HTTPS 凭据。

main 检查失败时仍可查看已加载的分支列表；release 的 MR 查询与 main 检查分别展示结果。

### 创建 MR 失败

检查 Token 的有效期及 `api` 权限、项目访问权限、源与目标分支是否存在、源代码是否已推送，以及 GitLab 是否已存在相同方向的开放 MR。可在 GitLab 中确认现有 MR 后再处理，避免重复创建。

### release 没有对应 feature

检查两者路径第二段是否一致，例如 `release/2.8.0` 对应 `feature/2.8.0/...`，不对应 `feature/2.8/...`。

### Reviewer 未匹配到用户

使用 GitLab 用户名而不是显示名称，并确认该用户对当前 GitLab 实例可见。任一账号未匹配、用户名为空或查询失败时，不会提交 MR；根据错误提示修正 `gitlabMr.defaultReviewers` 后重试。GitLab 返回的权限或指派错误也会直接显示，不会自动移除 Reviewer 后重新提交。

例如配置账号 `gitlab_reviewer` 时，应填写 `"gitlabMr.defaultReviewers": ["gitlab_reviewer"]`，而不是字符串 `"gitlab_reviewer"`。运行 **GitLab MR: Show Logs**，查看以下日志：

- `[Reviewer 配置]`：生效值以及用户、工作区、文件夹配置，便于定位覆盖问题。
- `[Reviewer 账号解析]`：用户名、返回的账号 ID 及匹配结果。
- `[Reviewer 创建请求]`：提交给 GitLab 的 `reviewer_ids`。
- `[Reviewer 创建响应]`：GitLab 返回的 MR 编号和 Reviewer 列表。

若创建响应未确认配置的审核人，扩展会明确提示“MR 已创建，但未确认 Reviewer”；应打开已有 MR 核对，不要重复创建。日志不记录 Token；分享前仍需移除内部地址等敏感信息。

### 如何查看错误详情

运行 **GitLab MR: Show Logs**，或点击错误通知中的“查看详细日志”。分享日志前请检查并移除凭据、内部地址及其他敏感信息。

### “GitLab 工作台”出现在 Explorer，或提示 View container does not exist

更新到修正视图容器声明的扩展版本后，运行 **Developer: Reload Window（开发人员：重新加载窗口）**；扩展开发模式下需重新启动扩展开发宿主窗口，使 VS Code 重新读取扩展声明。

如果视图仍位于 Explorer，可运行 **View: Reset View Locations（视图：重置视图位置）**。此命令会重置其他视图的自定义位置，请按需使用。

## 十、推荐日常流程

1. 推送本次代码到 GitLab。
2. 打开“GitLab 工作台”中的“分支管理”，必要时刷新分支。
3. 使用“搜索分支”定位版本或工单。
4. 点击分支的检查按钮，查看分支下一级结果。
5. 根据结果打开已有 MR，或按推荐目标创建 MR。
6. 到 GitLab 完成审核、流水线检查和合并。
7. 合并后重新检查相关分支；远程分支增删后刷新列表。

## 十一、操作审计

### 查看历史与导出

打开 **GitLab 工作台 → 操作审计**：

1. 顶部显示存储健康状态、文件数量、占用字节，以及扩展运行主机上的实际目录。
2. 历史按时间倒序，每页 50 条，通过页尾“上一页 / 下一页”切换。一个操作会有多条阶段事件，不等于多次执行。
3. 点击事件，在编辑器中查看同一 `operationId` 的 JSON 时间线，包括请求、确认、准备执行、成功、失败、结果未知、取消或阻止。操作详情不包含代码或凭据。
4. 点击筛选按钮，按项目 ID/路径、操作系统或 GitLab 用户、操作类型、风险、状态、起止时间及分支/MR关键词组合筛选。多次选择会叠加条件；留空清除单项，“reset”清除全部。时间须包含时区，例如 `2026-10-19T00:00:00+08:00`。
5. 常用类型为 `branch.delete`、`mr.approve`、`mr.merge`、`mr.create`、`token.set`、`token.clear`；风险为 `normal` / `sensitive` / `high`，状态为 `success` / `failed` / `unknown` / `blocked` / `cancelled` / `prepared` / `requested` / `confirmed`。`unresolved` 专门筛选执行准备后未记录终态的操作。
6. 点击导出按钮选择 CSV 或 JSONL，再选择扩展运行主机上的新文件；导出的是**当前筛选范围的全部事件**，不是当前页。不覆盖已有文件，也不允许导出到原始审计目录。CSV 对公式前缀做了转义；JSONL 首行为版本/导出时间/筛选元数据，末行为条数摘要，CSV 的 `export_summary` 元数据行提供同等说明。

导出本身也先写审计准备记录，成功终态在文件完成后追加到原始日志，因此不包含在本次导出快照内。导出文件含内部项目、分支、用户名和主机信息，应按内部资料保护。

### 存放位置与卸载

| 扩展运行主机 | 独立目录 |
| --- | --- |
| Linux | `~/.local/state/gitlab-mr-tool/audit/` |
| macOS | `~/Library/Application Support/GitLab MR Tool/audit/` |
| Windows | `%LOCALAPPDATA%\GitLab MR Tool\audit\`（环境变量缺失时使用用户目录下 `AppData\Local`） |

日志不使用项目目录、扩展安装目录、VS Code 用户数据目录或临时目录。正常卸载 VS Code / 扩展不会主动删除这些日志；重新安装后仍读取同一目录。扩展没有清空入口，不自动过期删除。

Remote SSH / WSL 在**远端扩展宿主**保存，而非本地 UI 主机。容器、临时虚拟机、用户目录清理、重装系统可能丢失文件，请挂载持久存储并安排备份。多窗口使用独立 JSONL 流，按 UTC 日期或文件达到 10 MiB 后轮换，逐文件序列号和 SHA-256 哈希链用于发现损坏；新建目录/文件在 Unix 上分别使用 0700 / 0600 权限。底层存储需支持可靠的 append / fsync。

**本地日志不是不可篡改存证。** 拥有目录权限的用户或管理员依然可以删除、截断或改写；完整性校验不能证明整段日志未被删除，也不能阻止有权限者重算哈希。若将来要求强制留存、抗管理员删除或合规存证，需要可信服务端/WORM 存储。

### 记录范围与失败处理

- 删除分支、Approve、Merge、创建 MR、本扩展保存/清除 Token，以及导出操作，都在实际写入前持久化 `prepared` 记录；失败则不发出该写请求。
- 记录 UTC 时间、操作 ID、阶段、耗时、OS 用户、主机、扩展版本，以及白名单内的实例、项目、分支、MR、SHA、Reviewer 和创建选项。GitLab 身份只在核实后记录，`gitlabIdentity: unknown` 表示未核实，不代表未认证执行；不会复用其他服务实例或 Token 的用户。
- 不记录 Token/密码/凭据摘要、请求头、代码正文、MR 标题/描述、原始响应或任意错误文本；仅记录受控错误分类和 HTTP 状态。现有诊断 Output 日志与此审计模块相互独立，分享时仍需检查敏感信息。
- 普通命令的 `command.* / requested` 仅代表用户发起，不宣称执行成功；另记录复制分支、加载变更、打开 Diff/浏览器等成功事件。打开 Diff 不等于已审阅全部文件。自动回调不伪装人工操作，每分钟更新时间间隔不写审计。
- 关键配置和 SecretStorage 外部变化记为 `config.observed` / `token.observed`，仅记设置名称，不记录配置原值；这些变化发生在通知之前，扩展**不能阻止或回滚用户从设置面板进行的修改**。
- 远端确认成功、但结果日志写入失败时，会明确提示“操作已成功，审计失败”，暂停后续敏感操作，**不要再次删除、批准或创建 MR**。请求已经发出但响应或审计无法确认时，也明确提示核实，不自动重试。
- 网络错误、5xx、408、无效/未确认的成功响应记为 `unknown`；其他明确 4xx 拒绝记为 `failed`。只有 `prepared` 而没有成功/失败/未知终态时，历史标记待核实，不推断远端失败；应到 GitLab 核对。
- 存储不可写、磁盘满或发现损坏时修复存储问题，再点击健康状态或运行 **GitLab MR: 校验并恢复审计存储**。该操作校验已有记录并 fsync 写入探测；不会自动裁剪损坏尾行或删除历史。日志损坏时先备份并由管理员处理，不能通过恢复按钮绕过校验。其他窗口正写入导致快照不稳定时，稍后刷新再试。

本模块只覆盖本扩展可观察的操作，不追溯安装前历史，也不捕获浏览器、CLI、其他扩展或其他用户的操作。尚未在真实 GitLab、三平台卸载/重装或远端宿主环境完成验收，应按实际部署环境验证。

## 新建发布与冲突处理分支

命令面板搜索「新建 release 分支」「新建 hotfix 分支」或「新建 conflict 分支」，也可通过分支管理标题栏的新建按钮操作。

选择基线类型（分支或 Tag，conflict 固定为目标分支），输入关键词搜索并选择具体基线。release 填版本号；hotfix 填版本、工单号和可选英文描述。conflict 填写原始 release/hotfix 分支的完整名称，不再单独填写版本或工单。核对完整 SHA 后点击「确认创建」。

处理冲突时，在准备合回的目标分支上右键选择「新建 conflict 分支」。创建的是目标分支的副本，不会自动执行 merge。随后将待合入代码合并到该副本、解决冲突并测试，最后从 conflict 分支向原目标分支发起 MR。

只创建 GitLab 远程分支；不会切换或修改当前工作区文件。取消确认不会创建分支。基线更新、重名或权限不足会阻止创建，网络结果不确定时请先在 GitLab 核对，避免重复操作。

conflict 分支默认展示，并保留原始分支层级：`hotfix/H20260706/FOC-0009` → `conflict/hotfix/H20260706/FOC-0009`；`release/LI2500076` → `conflict/release/LI2500076`。命名来源和创建基线分开选择：名称来自原始分支，代码基线来自准备合回的目标分支。原始分支需存在，确认框会同时展示原始分支与目标基线信息。升级时自动补齐旧默认筛选中的 conflict，自定义筛选保持不变。
