# VS Code conflict 处理向导与审批状态栏

## 从有冲突的 MR 开始

在“我的待办”的冲突 MR 上执行“处理冲突 / 创建 conflict 分支”。完整向导适用于 GitLab 同仓库的 release/hotfix → dev/tst/uat/pre，沿用规范中的 Target 基线和 `conflict/<完整 Source>` 名称。

1. 打开对应仓库，选择独立 worktree（推荐）或当前工作区。当前工作区模式必须没有未提交改动及未完成的 Git 操作。
2. 确认后，插件关闭原 MR、从 Target 创建 conflict、准备本地分支并合入所确认的 Source 提交。独立 worktree 在相邻目录创建，并在新窗口打开，原工作区保留。
3. 在源代码管理中解决冲突、逐文件检查和暂存，并执行相关测试。待办视图标题栏及命令面板提供“继续 conflict 处理”入口，未解决文件可从该入口打开合并编辑器。
4. 继续任务时展示暂存差异，填写真实模块、工单及原因，确认后提交并普通推送。不会自动暂存文件、强推或自动解决冲突。
5. 插件固定原 Target，预览替代 MR 描述，确认标题和 Reviewer 后创建 MR。描述保留分支、工单、自检等模板内容，提交和文件清单只取已推送提交相对最新远程 Target 的实际差异，附原 MR 链接。继承原 MR 的 Reviewer ID；原 MR 未指定审核人时会明确提示补充。
6. 替代 MR 固定合并后删除源分支、不 Squash。合并完成后再次继续任务，可核对并清理远程 conflict、归档任务。清理依据为替代 MR 合入原 Target，另检查 SHA、保护状态、默认分支及其他开放 MR。不会要求合入 main，也不会自动删除本地 worktree。

从分支管理直接创建 conflict 的入口仍提供原有分支与指南流程；完整可恢复向导需要原 MR 关联。GitHub 的冲突 MR 查询及完整处理向导尚未接入。

## 恢复与边界

任务保存于 VS Code 的全局扩展存储，绑定实例、项目、原 MR、源/目标、SHA、路径及阶段。重启后可继续；此存储不是团队共享的任务系统。

关闭旧 MR、创建分支、准备工作区、推送和创建替代 MR 分阶段记录。发生错误时保留任务，从“继续 conflict 处理”重新核对远程状态。分支同名但无任务关联时不接管；同一 Source 对其他 Target 的任务不会覆盖现有分支。多个开发者仍需协调同名 conflict 的占用。

创建 MR 响应丢失时先分页查询已有 MR，不自动重复 POST。未查到时要求先到 GitLab 核对，明确确认不存在后才允许重试。基线变化需重新确认；本地分支、origin 或任务版本不匹配时暂停。

原 MR 关闭后若不再继续处理，需要在 GitLab 人工核对并重新打开原 MR。插件不会自动重新打开旧 MR或放弃当前合并。人工中止 merge 后，继续任务可确认重新准备。任务归档不删除工作区文件。

## 待审批状态栏

- 展示“待审批 N”，统计当前 GitLab 实例中指定本人为 Reviewer 且尚未批准的开放 MR；合并、关闭或本人已批准的 MR 不计入。
- 有待审批项时高亮。点击打开“我的待办”并刷新，随后可展开“待我审批”。
- 默认每 60 秒静默刷新，`gitlabMr.approvalRefreshSeconds` 可设为 30–600 秒。新 MR 在下次成功刷新后计入。
- 后台计数独立于待办树，不清空正在查看的 Diff。手动刷新、批准后刷新及连接变更也会更新计数。
- 查询失败显示 `?`，未配置凭据或平台尚未支持则显示 `—`，不将未知状态显示成 0。GitHub 待审批计数仍待后续适配。

## 验证

`test:conflict-session` 包括真实临时本地 Git 仓库的 worktree/冲突/提交/推送测试，以及模拟 GitLab API 的关闭与清理、状态栏计数和失败显示测试。没有使用公司真实 GitLab 执行关闭、推送或删除操作。
