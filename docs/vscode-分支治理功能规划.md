# VS Code 分支治理功能规划

依据：[代码仓库与分支规范](代码仓库与分支规范.md)。本文件区分本次实现与后续规划；后续项目不代表已交付。

## 本次实现：release / hotfix 的 conflict 创建与处理引导

适用场景：`release/*` 或 `hotfix/*` 合入 `dev`、`tst`、`uat`、`pre` 时发生冲突。

1. 在“分支管理”右键 release / hotfix →“新建 conflict”，自动带入原始源分支。从测试环境分支右键进入时，优先展示该目标；从命令面板进入时，可搜索并分页选择远程源分支。
2. 目标只列实际存在的四类测试环境分支，不能误选 main、原始源分支或任意分支。没有目标时停止；除 404 外的查询失败直接报错，避免把权限或网络错误当成不存在。
3. 名称为 `conflict/<完整源分支名>`，例如 `conflict/release/LI2500076`、`conflict/hotfix/H20260706/FOC-0009`。
4. 按规范第 3.6 节的详细步骤，以**目标环境分支**作为创建基线。确认窗口展示源、目标及 SHA；创建前复核源与目标是否变化，变化则要求重新预览。
5. 同名 conflict 已存在时停止创建，提示核对现有 MR / 处理进度；不覆盖、不自动追加环境名。规范名称不含目标环境，因此同一源分支对多个环境的处理必须避免并发占用同名分支。
6. 创建后打开 Markdown 指南，列出关闭原 MR、fetch、切换 conflict、合入原始源分支、人工解决、测试、提交、推送、重新提 MR 的具体步骤。指南使用 Git Bash / POSIX Shell；不执行本地 Git 写操作，也不自动关闭 MR。
7. VS Code 所有 MR 创建路径对 `conflict/*` 固定 `remove_source_branch=true`、`squash=false`，标题确认提示同步显示此规则，不受全局相反配置影响。其他分支沿用原配置；Web / API 版本链路不变。
8. 创建后的编辑器、剪贴板或浏览器操作失败，仍反馈远程创建已完成，避免用户误以为失败而重复提交。

### 我的待办与 MR 快捷创建（已实现）

- “我的待办”包含“我提交的 MR”和“待我审批”，各自按项目分组，默认只加载开放中的 MR，包含草稿。我提交的 MR 不因已获审批而隐藏；同一 MR 同时满足两个角色时会出现在两个分组，计数分别表示各角色列表数量。
- 有代码冲突的 MR 使用红色图标，并显示“有冲突”。GitLab 正在计算、未返回状态、状态查询失败时显示对应说明，不把未知当成已确认无冲突。两类列表独立加载，单类失败不会隐藏另一类。
- 在红色 MR 上点击分支图标，或展开后点击“创建 conflict 分支…”文字按钮。所有 MR 的右键菜单及命令面板也提供“处理冲突 / 创建 conflict 分支”入口。符合规则时自动使用 MR 所属项目、source、target 和最新 SHA；无需打开对应仓库、手工输入分支或再次选择目标。
- 快捷入口支持同仓库 release/hotfix → dev/tst/uat/pre。跨仓库 MR 或其他流向仍标红并保留处理入口；展开后显示“查看冲突处理方式”，点击后说明应采用的流程，不再直接隐藏入口。
- 创建前复核 MR 仍开放、确有冲突、分支和 SHA 未变化；确认后再次检查。MR 已关闭、已合并、正在计算、冲突消失、源/目标变化、同名 conflict 已存在或待办已刷新失效时停止操作。
- 处理指南包含原 MR 链接及固定的源、目标，便于后续关联和重新提 MR。

当前边界：插件创建 conflict 分支并生成指南，不自动关闭原 MR，也不执行本地合并；因此原 MR 在冲突未消除前会继续标红。向导关联尚未持久化，重新提 MR 时仍需按指南选择原目标。

## 日志输出

默认只输出关键操作结果和需要处理的警告、错误。API 成功请求、Git 命令、分支列表、工单链接渲染、Reviewer 解析和界面流程等详细信息默认关闭；正常的 404 分支探测不单独输出错误，实际失败由上层操作报告，避免重复记录。

需要排查问题时，可在 VS Code 设置中启用 `gitlabMr.verboseLogging`，无需重启；关闭后立即停止详细输出。诊断日志不输出 API 请求正文或完整响应正文，审计记录保持原有行为。

## 场景与后续处理方式

| MR 场景 | 规范路径 | 本次范围 / 后续方案 |
| --- | --- | --- |
| feature / bugfix → release；hotfix → main | 在原始 Source 合入 Target，人工解决后推回 Source，继续原 MR | 后续提供“在源分支处理”向导，不创建 conflict |
| release → main | Tech Leader 在原始 Source 处理，继续原 MR | 后续读取角色 / 保护规则并引导，不替代 GitLab 权限检查 |
| release / hotfix → 测试环境 | Target 派生 conflict，合入 Source，处理后 conflict → 原 Target | 本次创建、MR 快捷入口与指南关联已实现；持久化状态机列为 P0 |
| main → release / 测试环境 | 文档提供 Tech Leader 与 Developer 两条路径 | 命名和推送目标存在歧义，暂不生成可执行流程；等待规范维护者明确 |

建议下一步先完成持久化状态关联和恢复，再接入本地处理向导，随后补充定向清理和 MR 预检。

## 需要规范明确的事项

- conflict 分支表写从 hotfix / release 派生，详细步骤写从 Target 派生。本次采用详细步骤，与插件原有从目标创建的意图一致，并在确认及指南中说明。
- main 回流 Developer 路径需要 conflict，但未定义其分支名；不自行引入 `conflict/main` 或新的后缀格式。
- main 回流 Tech Leader 路径写“切换 Target，却 push Source”，需要明确实际推送目标及保护分支的允许操作。
- 相同 Source 对多个 Target 的并发冲突共用一个规范名称，是否允许目标后缀或要求串行，需统一规则。本次不扩展命名。

## 验证范围

- 我的待办：作者查询分页、角色分组、双重角色、草稿、红色冲突图标、未知状态、单类失败与过期响应；从 MR 创建时绑定正确项目和源/目标、确认后状态复核、取消、重复分支和跨仓库阻止。

- 模拟 GitLab API：源分支带入、目标基线、同名分支、取消、源 / 目标 SHA 变化、权限失败、创建后界面失败，以及 conflict MR 选项覆盖。
- 分页选择：前页无有效源分支但仍有下一页时可继续选择。
- 临时真实 Git 仓库：运行指南生成的 fetch / switch / merge 命令，验证冲突发生在从 Target 派生的 conflict 分支；人工解决后仅推送 conflict，远程 Source / Target 保持原提交。
- 工作区原有被删除的基础模块不由本次恢复；验证在临时副本中使用 HEAD 的对应基础文件完成。因此验证结果不表示当前工作区的整包构建已解除这些缺失文件的影响。
